# 보조정리 사냥꾼 예약 실행 (2026-11-06)

`.github/workflows/claude-lemma-hunter.yml` 을 하루 1 회 예약 실행한다. 작업 선택은 `scripts/hunt_select.py` 가 결정적으로 하고
(AI 없음), 시험은 `tests/test_hunt_select.py` 다. 사냥꾼 자체 (150 턴, 150 분, Opus, draft PR) 는 바꾸지 않았다.

## 실행

- 예약: `cron: "37 0 * * *"` = 매일 09:37 KST (정각 혼잡을 피한다).
- 수동: `workflow_dispatch`. issue 입력을 주면 사용자가 그 이슈의 재시도를 지정한 것으로 본다.

| job | AI | 쓰기 권한 | 하는 일 |
| --- | --- | --- | --- |
| select | 없음 | 없음 | 작업 하나를 고르거나, 고를 것이 없으면 끝난다. 판정할 수 없으면 실패한다 |
| mark | 없음 | issues | 고른 이슈에 시작 기록 댓글을 남긴다. 실패하면 hunt 는 시작하지 않는다 |
| hunt | Claude (구독) | 없음 (App 토큰으로 `claude/hunt-*` 브랜치와 draft PR) | 기존 사냥꾼. select 가 검증한 번호와 본문만 작업 파일로 받는다 |

## 선택 규칙 (예약 실행)

1. 열린 연구 PR (head 가 `claude/hunt-*`, Draft 와 Ready 모두) 이 2 개 이상이면 새 작업을 시작하지 않는다. 검토 대기가 쌓이지 않게 한다.
2. 후보는 열린 `lemma-hunt` 이슈 가운데 소유자가 쓰고 본문을 소유자 말고는 고친 적 없는 것 (GraphQL `author`, `editor`).
3. 열린 또는 병합된 연구 PR 의 본문이 그 이슈를 `Refs/Closes/Fixes/Resolves #N` 으로 가리키면 고르지 않는다.
   병합 없이 닫힌 PR 은 연결로 치지 않는다 (아래 4 가 같은 시도의 반복을 막는다).
4. 같은 이슈 본문 (해시) 과 같은 기준 main SHA 로 시작한 기록이 있으면 결과와 무관하게 고르지 않는다.
   본문을 고치거나 main 에 커밋이 들어가면 (문서 커밋 포함) 다시 고를 수 있다.
5. 남은 것 가운데 번호가 가장 작은 이슈.

명시적 수동 실행은 4 만 건너뛴다. 1 (열린 연구 PR 2 개 한도) 과 2·3 (신뢰·중복) 은 그대로다. 고를 수 없으면 실패로 끝나 이유가 보인다.

## 시작 기록

mark job 이 `github-actions` 봇으로 이슈에 댓글을 남긴다. 판정에 쓰는 것은 사람용 문장이 아니라 고정 표식이다.

```
<!-- lemma-hunt-attempt: v1 task=<본문 sha256> base=<main SHA 40 자리> outcome=started run=<run_id>.<run_attempt> -->
```

- 비싼 Lean 준비와 AI 실행 전에 남기므로 시간 초과나 취소로 끝나도 기록이 남는다. 결과 (PR 또는 실패 보고) 는 같은 실행의 기존 출력 확인 단계가 본다.
- select 는 `github-actions` 봇이 쓴 댓글의 표식만 믿는다. 사람이나 `claude` 앱이 쓴 같은 모양의 문자열은 무시한다.
- 이슈 댓글은 AI 에게 보이지 않는다. 결정적 선택기만 읽는다.

## 판정할 수 없을 때

열린 `lemma-hunt` 이슈 50 개, PR 200 개 (상태 무관), 이슈당 댓글 100 개, 이슈당 라벨 20 개가 상한이다. 상한 + 1 로 조회하거나
`totalCount` 와 실제 개수를 비교해, 넘치거나 잘렸으면 작업을 시작하지 않고 실패한다. 기준 SHA 가 40 자리가 아니거나
명시한 이슈를 찾지 못해도 실패한다.
